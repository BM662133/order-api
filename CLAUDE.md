# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Order API: Spring Boot 3.5.x (Java 21, Maven), root package `com.example.orders`. Partners order a SIM/plan for a subscriber; orders move through the `OrderStatus` state machine. Built in slices (see `git log`). Stay on Spring Boot 3.x (start.spring.io only generates 4.x, so don't regenerate from it).

`README.md` is the user-facing guide: how to run, curl walkthroughs, error table, config properties. Keep it in sync when endpoints, status codes, `orders.*` properties or the fake gateway's MSISDN rules change.

Packages are by feature: `common/error` (ProblemDetail handling), `common/time` (Clock), `tenant` (partner auth), `plan` (plan catalogue + `@KnownPlan`), `order/{api,app,domain,persistence}` (controller + DTOs → service → entity/state machine → repository), `order/history` (status audit trail), `outbox` (transactional outbox, relay, and the pluggable transport: in-process by default, `outbox/kafka` with the `kafka` profile) and `provisioning` (async worker that drives orders to a final status, fake carrier gateway).

## Commands

Use the Maven wrapper (`./mvnw`), not a system `mvn`.

- Build + run all tests: `./mvnw test`
- Single test class: `./mvnw test -Dtest=OrderApiApplicationTests`
- Single test method: `./mvnw test -Dtest=OrderApiApplicationTests#healthEndpointReportsUp`
- Run the app: `./mvnw spring-boot:run` (port 8080; health at `GET /actuator/health`)
- Run with Kafka: `docker compose up -d` (single-node Kafka from `compose.yaml`), then `./mvnw spring-boot:run -Dspring-boot.run.profiles=kafka`. Verified by hand against the `compose.yaml` broker: happy path, consumer retries to DLT, and broker outage plus recovery. Sends are batched (see Transports), so during an outage a relay pass waits at most one `delivery.timeout.ms` (10 s), however many events it holds, and an outage of any length spends no attempts. On this machine Docker is Colima (`colima start` / `colima stop`), not Docker Desktop.
- Package: `./mvnw package`

There is no linter or formatter configured.

## Architecture and conventions

- **Schema is owned by Flyway, not Hibernate.** `spring.jpa.hibernate.ddl-auto=validate`, so every new `@Entity` needs a matching migration in `src/main/resources/db/migration/` (`V<n>__<description>.sql`), or the app fails to start. Never edit an applied migration; add a new one.
- **Database** is in-memory H2 (`jdbc:h2:mem:orders`), recreated on every start — no data persists between runs or tests.
- `spring.jpa.open-in-view=false`: load whatever a response needs inside the service/transaction layer, not lazily in controllers.
- **Actuator** exposes only the `health` endpoint over HTTP (`management.endpoints.web.exposure.include`).
- **Lombok** is optional and configured as an annotation processor in `pom.xml`; it is excluded from the packaged jar.
- **Smoke test** `OrderApiApplicationTests` boots the full app on a random port and asserts `/actuator/health` returns `UP` — it covers context startup, DB connection, and Flyway together. Keep it passing. It also asserts that the default mode creates no Kafka beans.
- `.gitignore` ignores all of `.claude/` (personal Claude Code settings). To share project-level config such as `.claude/commands/`, switch to `.claude/*` plus `!` negations; a file can't be re-included under an ignored directory.
- Use constructor injection, no field @Autowired
- Return RFC 7807 ProblemDetail for errors
- Every feature needs tests; run ./mvnw test after changes
- Keep controllers thin; logic lives in services

## Errors, tenancy and state

- **Errors:** throw a subclass of `common.error.ApiException` (it carries status, `type` URI, title and extra `properties()`); `GlobalExceptionHandler` renders it as `application/problem+json`. Add new `type` URIs to `ProblemTypes` and never change existing ones. Unexpected exceptions become a generic 500 — never put internal details in a response.
- **Partner auth:** `PartnerAuthenticationInterceptor` resolves the `X-Partner-Id` header (a stand-in for real auth) on the paths in `TenantWebConfig.AUTHENTICATED_PATHS` (`/partners/**`, `/orders/**`); missing/unknown/inactive → 401 with a `WWW-Authenticate: Partner realm="order-api"` challenge (an `ApiException` can add response headers via `headers()`). Controllers get the caller by declaring a `PartnerContext` parameter. New API paths must be under those patterns. A route path variable named exactly `{partnerId}` is checked against the caller by the interceptor (403 `partner-mismatch`, before body validation) — name it that way and don't re-check it in controllers.
- **Tenant isolation:** repositories extend Spring Data `Repository` (not `JpaRepository`) and declare only the finders they need; tenant-owned data is looked up by `partnerId` as well as id, and another partner's resource is a 404, never a 403. The one exception is `ProvisioningSweepQueries`, the sweeper's cross-partner reads. They return only (id, partner), and every follow-up load or write goes through the scoped paths.
- **Status changes** happen only through `Order`'s methods (`transitionTo`, `fail`, `cancel`, `completeCancellation`). All of them funnel into the private `changeStatus`, which checks `OrderStatus.canTransitionTo` (throwing `IllegalTransitionException`, 409) and records the history event. Never set status any other way, or the change escapes both checks. Allowed transitions are declared in `OrderStatus`'s exhaustive `switch`; update `OrderStatusTest.LEGAL` alongside it.
- **Inject `Clock`** instead of calling `Instant.now()`, so tests can control time.
- **Idempotent create:** `POST /partners/{partnerId}/orders` requires `Idempotency-Key` (1–100 visible ASCII).
  - **Guarantee:** a key is reserved in `idempotency_keys`; its unique constraint `uq_idempotency_keys_partner_key (partner_id, idempotency_key)` is the guarantee.
  - **Expiry:** each reservation expires `orders.idempotency.key-ttl` (24h) after the order was created. An expired key counts as unused: `OrderWriter.insert` deletes its row before reusing it, and `IdempotencyKeyPurge` cleans up hourly. `orders.idempotency_key` stays on the order as a record of the key that created it, and is no longer unique.
  - **Transactions:** `OrderService.create` is deliberately **not** `@Transactional`. The insert (delete expired key, insert order, insert key, outbox event) runs in `OrderWriter`, a separate bean using `saveAndFlush`, so a duplicate-key `DataIntegrityViolationException` can be caught outside the failed transaction and the winner re-read.
  - **Outcomes:** same key + same normalized request (`RequestFingerprint`) → replay (201 + `Idempotent-Replayed: true`, current order state); different request → 422.
  - **Order of checks:** `@Valid` format checks on `CreateOrderRequest`, then key format, then replay, and only then the checks that depend on database state (`@KnownPlan` on `CreateOrderCommand`, run by `OrderService` → `RequestValidationException`, same 400 shape). A retry must replay even if its plan has been deactivated since; put any new database-dependent check on the command, not the request.
  - If you add a create-request field, add it to `RequestFingerprint` and bump its `v1` prefix.
- **Cancel** (`POST /orders/{id}/cancel`) goes through `Order.cancel`, which returns a `CancelOutcome`: CREATED/VALIDATED → CANCELLED (200); already CANCELLED → 200 no-op (no write); PROVISIONING → sets `cancel_requested_at`, status unchanged (**202**; a repeat is a 202 no-op); ACTIVE/FAILED → 409 `illegal-status-transition`. Only the provisioning worker takes PROVISIONING → CANCELLED, via `Order.completeCancellation` after `gateway.deactivate` (compensation).
- **Status history:** every status change (including creation) is recorded by `Order` as an `OrderStatusChanged` (from, to, reason, `TriggeredBy` CLIENT/SYSTEM, occurredAt). Spring Data publishes them on any repository `save*` (`@DomainEvents`), and `OrderStatusHistoryRecorder`, a plain `@EventListener`, inserts `order_status_history` rows in the same transaction. Keep it that way, not `AFTER_COMMIT`: a rolled-back change must take its history with it. So a new write path gets history automatically as long as it saves through `OrderRepository`; never change status with SQL in main code. Only status changes are recorded (a cancel request is not one). Read via `GET /orders/{id}/history` (partner-scoped, 404 like GET).
- **Outbox:** a state change that something must react to records an event with `Outbox.append(aggregateId, partnerId, type, messageKey, payload)` inside the same transaction (`Propagation.MANDATORY` enforces that; see `OrderWriter.insert` → `OrderCreated`). `OutboxRelay.relayDue()` loads a batch of due events (`OutboxRepository.findDue`) and hands it to `OutboxTransport.deliverAll`, which returns a `DeliveryResult` per event (Delivered, Failed, Unavailable or NotAttempted). The relay then records every outcome in one `saveAll` transaction: Failed is retried with exponential backoff (`orders.outbox.*`) and is DEAD after `max-attempts`, at which point `transport.onDead` runs; Unavailable and NotAttempted are left untouched, with no attempt counted.
  - **Unavailable** means the transport itself is down, which says nothing about the event. After such a pass the relay pauses itself (in memory, not per row): `initial-backoff`, doubling to `max-backoff`, reset by the next pass without one. So an outage never makes events DEAD; they wait until the broker is back. Only a transport that can tell its own outage apart from a bad event may return it; the default `deliverAll` (in-process) never does, so a handler's `GatewayUnavailableException` still counts attempts and the order reaches `PROVISIONING_UNAVAILABLE`.
  - **Same key, in order** is a real guarantee: `findDue` is head-of-line per `message_key`. An event waits while an *older PENDING* event with its key exists, even one backing off after a failure, so a batch never holds two events for one key. Older DEAD or PROCESSED events don't block. Consequence in tests: two events with one key need two relay passes (use `drain`).
  - Handlers implement `OutboxEventHandler` (taking an `EventEnvelope`, never the entity), are routed by `OutboxEventHandlers`, and must be idempotent. `OutboxSchedulingConfig` polls the relay; it is single-instance only (multi-instance would need `FOR UPDATE SKIP LOCKED`).
- **Transports** (`orders.outbox.transport`):
  - `in-process` (default): the relay calls the handler, so relay retries are handler retries, and DEAD → `onRetriesExhausted`.
  - `kafka` (profile `kafka`): the relay publishes to `orders.events` and marks the row PROCESSED on the broker ack. `KafkaTransport.deliverAll` sends the whole batch, then waits for all acks against one `send-timeout` deadline (measured on the compose broker: 500 events in 337 ms, against 2,007 ms when sending one at a time). A failure whose cause chain holds a Kafka `RetriableException` (metadata or delivery timeout, network or leader errors, all already retried by the producer) or our own `send-timeout` is Unavailable; anything else (e.g. `RecordTooLargeException`) is Failed for that event only. If a send is Unavailable immediately (broker unreachable, metadata timeout after `max.block.ms`), it stops the batch and returns the rest as NotAttempted; an immediate Failed does not stop it. The format is in `OutboxKafkaCodec`: key = message key, value = payload, headers `eventId`/`eventType`/`aggregateId`/`partnerId`.
  - With Kafka, `OutboxKafkaListener` runs the handler. `DefaultErrorHandler` retries in place with the same backoff, then `OutboxDeadLetterRecoverer` calls `onRetriesExhausted` and dead-letters to `orders.events.DLT`. Unreadable records and unknown types are not retried.
  - A Kafka *publish* that goes DEAD (only for non-retriable errors now, never for an outage) does **not** fail the order (the gateway was never tried): it only logs, and you republish by setting the row back to PENDING.
  - Every Kafka bean is `@ConditionalOnProperty(transport=kafka)`, so the default mode never touches a broker (asserted in `OrderApiApplicationTests`).
  - Order events are keyed `partnerId:msisdn` (`OrderEvents.messageKey`), so same-MSISDN orders share a partition and validate serially even with several consumers.
- **Provisioning:** `ProvisioningWorker` handles `OrderCreated` by re-reading the order and acting on its *current* status in a loop (CREATED → eligibility → VALIDATED/FAILED → PROVISIONING → activate → ACTIVE, or deactivate → CANCELLED when a cancel was requested). Each step is a short transaction in `ProvisioningSteps` that no-ops unless the order is still in the expected status, and gateway calls run outside transactions. A permanent gateway rejection → FAILED `GATEWAY_REJECTED`. `GatewayUnavailableException` propagates so the relay retries, then FAILED `PROVISIONING_UNAVAILABLE` / `COMPENSATION_FAILED`. Failure reasons are the `FailureReason` enum (`failureReason` in responses). The worker uses the partner-scoped finder with the event's `partner_id`; there is still no unscoped order lookup. `FakeProvisioningGateway` remembers active lines: an MSISDN ending `0000` is rejected, and one ending `0001` is always unavailable.
- **Sweeper** (`ProvisioningSweeper`, every `orders.provisioning.sweep.interval`):
  - An unfinished order untouched for `stalled-after` (15m) with no PENDING event gets a `ProvisioningRetryRequested` event. `ProvisioningRetryHandler` delegates it to the worker.
  - FAILED orders with `PROVISIONING_UNAVAILABLE` / `COMPENSATION_FAILED` are checked with `gateway.isActive`; a still-active line is deactivated, then `reconciled_at` is set. That is not a status change, so it adds no history row. If the gateway is down, the sweeper retries on the next run.
- **Concurrent updates:** `Order` has `@Version`. Write use cases run in `OrderWriter` (`saveAndFlush`) and `OrderService` retries on `ConcurrencyFailureException` (up to `MAX_CANCEL_ATTEMPTS`), re-reading the order each time; give new update use cases the same shape. Anything that escapes becomes 409 `concurrent-modification` via `GlobalExceptionHandler`.
- **Concurrency tests** use `support/Concurrently.run(threads, ...)` with a `RANDOM_PORT` context; also cover the retry/race branch with a deterministic Mockito test, since thread timing isn't guaranteed.

## Testing notes

- `@WebMvcTest` must name its controllers (`@WebMvcTest(controllers = ...)`) and declare `@MockitoBean PartnerRepository`, because `TenantWebConfig` needs it.
- Test-only controllers are static nested `@RestController`s inside the test class, registered with `@Import`; Spring Boot's `TestTypeExcludeFilter` keeps them out of other test contexts.
- **Background jobs are off in tests.** `src/test/resources/config/application.properties` layers on top of the main `application.properties` and sets `orders.outbox.scheduling-enabled=false`, `orders.outbox.initial-backoff=0s`, `orders.idempotency.purge-enabled=false` and `orders.provisioning.sweep.enabled=false`. Every test context shares one H2 database, so a live scheduler in any cached context would process other classes' data.
  - Call `OutboxRelay.relayDue()`, `IdempotencyKeyPurge.purgeExpired()` and `ProvisioningSweeper.sweep()` directly, and settle leftover events in `@BeforeEach` with `OutboxTestSupport.drain` (see `ProvisioningFlowTest`). With zero backoff, N `relayDue()` calls are N real attempts.
  - Only `ProvisioningEndToEndTest` turns scheduling on, with `@DirtiesContext` so its scheduler stops afterwards.
  - `OutboxKafkaIntegrationTest` runs the `kafka` profile against `@EmbeddedKafka` (no Docker), also with `@DirtiesContext`. Consumption there is asynchronous, so it uses Awaitility. To prove that a no-op record was consumed, follow it with a same-key record (same partition) and wait for that one.
  - Provisioning tests need unique MSISDNs (`OutboxTestSupport.uniqueMsisdn`), because other tests' orders share `+447700900123` and would trip `MSISDN_IN_USE`.
- Shared test helpers in `support/`: `Concurrently`, `OutboxTestSupport` (`drain`, `uniqueMsisdn`) and `StatusHistory` (`timeline` as compact strings like `"CREATED->VALIDATED by SYSTEM"`). Setting status with SQL in tests bypasses history, so don't assert timelines for those orders.
- Seed data from `V1__partners_and_plans.sql` is available in `@SpringBootTest`: partners `partner-a`, `partner-b` (active), `partner-suspended` (inactive); plans `BASIC_5G`, `UNLIMITED` (active), `LEGACY_3G` (inactive).
